# Design patterns

## Data flow

Every file must move through one pipeline, with each stage in its own module under `src/`:

```
inspect -> strip / encode / svg -> decode -> score -> search -> select -> write
```

- `inspect/` reads the format (from magic bytes, never the extension), dimensions, alpha, animation and metadata.
- `strip/` removes metadata losslessly, `encode/` wraps the sharp encoders and `svg/` wraps SVGO. Each produces candidate bytes.
- `metrics/` decodes each candidate and scores it against the decoded source, never against another candidate.
- `search/` finds the lowest passing quality for a format. It is pure, with the encoder and scorer injected.
- `pipeline/` applies the mode rules, picks the smallest passing candidate and writes it through the safe-write path. When no candidate beats the input, it writes the lossless strip instead.

A stage that rejects a file throws `OptimiserError` (`src/schema/`) with a code from `src/schema/codes.ts`. `optimiseFile` turns it into a `failed` result, so only an abort, an invalid option or a bug rejects.

## Inspection

`inspect` reads only the header through sharp's `metadata()`, and parses the few things sharp can't see.

- The format comes from the leading bytes: the PNG or JPEG signature, `RIFF....WEBP`, an `ftyp` box with an `avif` or `avis` brand, or XML whose root element is `<svg>`. Anything else fails with `E_UNSUPPORTED_FORMAT`.
- Animation fails with `E_ANIMATED`: more than one page in sharp, an `acTL` chunk before a PNG's image data, or an `avis` brand. The last two are checked before sharp reads the file, because libvips decodes only an APNG's default image and libheif can reject an AVIF sequence outright.
- `E_DECODE` means sharp or SVGO couldn't read the header. Damaged image data only shows up when a later stage decodes it.
- `exif`, `xmp`, `iptc` and PNG `text` come from sharp. `gps` is a GPS pointer in EXIF IFD0. `comment` is a JPEG `COM` segment before `SOS`, or an SVG comment other than a `<!--! -->` licence notice, which SVGO's `removeComments` keeps. `editor` is an SVG namespace on SVGO's `editorNamespaces` list, or a `<metadata>` element, which is what SVGO's `removeEditorsNSData` and `removeMetadata` plugins remove.
- An ICC profile is sRGB only when its description is exactly `sRGB`, `sRGB IEC61966-2.1` or `sRGB IEC61966-2-1 black scaled`. Any other profile counts as non-sRGB and is kept, because dropping a profile that isn't sRGB shifts colours.
- SVGs are parsed by SVGO, whose tree a plugin that changes nothing captures. `referencedIds` lists the defined IDs used through `href`, `url(#id)`, `aria-labelledby`, `aria-describedby` or a CSS `#id` selector.
- `rights` comes from `readRights` (see Rights) for every raster image, empty when it has none. An SVG has none.
- The container readers live beside `inspect`, shared with `strip/` and `rights/`: `jpegSegments.ts`, `pngChunks.ts`, `pngText.ts` (text chunk keywords and text, inflating at most 16 MiB), `riffChunks.ts` and `exifIfd0.ts` (IFD0's entries, which `hasGps` reads). `jpegSegments.ts`, `pngChunks.ts` and `riffChunks.ts` also build their segments and chunks (`buildJpegSegment`, `buildPngChunk` and `buildRiffChunk`), and `riffChunks.ts` holds the `VP8X` flags. The AVIF item readers, with the `iinf` and `iref` rebuilders, are in `strip/avifItems.ts`, and `iloc`'s parser, writer and `relocateItems` in `strip/avifIloc.ts`.

## Lossless strip

`stripLossless` edits a JPEG, PNG, WebP or AVIF file's segments, chunks or boxes and never touches the pixel data, so a strip decodes to the same pixels and scores 100. It keeps an allowlist and drops everything else, including unknown segments and chunks.

- **JPEG** keeps `APP0` JFIF, `APP14` Adobe, a non-sRGB `APP2` ICC profile (joined across segments before it is classified), the other non-APPn segments, and everything from the first `SOS` to `EOI`. It drops the rest, including bytes after `EOI`, such as an appended motion-photo video.
- **PNG** keeps critical chunks, the display chunks `tRNS`, `gAMA`, `cHRM`, `sRGB`, `cICP`, `mDCV` and `cLLI`, and a non-sRGB `iCCP`, copying them with their CRCs untouched. A text chunk with the keyword `XML:com.adobe.xmp` counts as `xmp`.
- **WebP** keeps `VP8X`, `VP8 `, `VP8L`, `ALPH` and a non-sRGB `ICCP`, then rewrites the `VP8X` ICC, EXIF and XMP flags and the RIFF size.
- **AVIF** removes the `Exif` and `mime` items (from `iinf`, `iloc`, `iref` and `ipma`, and their data from `mdat` or `idat`) and any `colr` property with an sRGB ICC profile, renumbering the `ipma` indices after it. Other properties, including `irot`, `imir` and `nclx` colour, are kept. The removal is `removeAvifItems` (`src/strip/removeAvifItems.ts`), which `setRights` shares. It rebuilds `meta` twice: once to measure how much it shrinks, then with every kept item's `iloc` offsets moved by that shrink and by the bytes cut before its data. Field sizes never change, and offsets only get smaller, so they always fit. The generic box and field helpers are in `src/strip/isobmff.ts`, where `FieldWriter` throws a `RangeError` for a value its field can't hold, a field of size 0 included.
- When the orientation isn't 1, the first EXIF block is replaced by a 26-byte TIFF holding only Orientation, with the block's original `Exif\0\0` header when it had one. An EXIF block no longer than that already holds nothing else and is kept as it is. This makes a second strip remove nothing and stops the replacement making a file larger.
- `removed` lists the kinds dropped: the `inspect` metadata kinds (with `gps` when the dropped EXIF had it), `icc`, and `other` for anything else, such as PNG `pHYs`. When it is empty, the input is returned as it is.
- A file whose structure ends early (no `SOS`, no `IEND`, a chunk past the RIFF payload, a truncated AVIF box or item table, or any field read past the end, which `stripLossless` maps from a `RangeError`) fails with `E_DECODE`.

## Rights

`src/rights/` reads the copyright, licence and AI-origin fields Google Images reads, builds the XMP packet that carries them, and writes it into a file. `ImageRights` holds Creator, Credit Line, Copyright Notice (every language alternative, `x-default` first), Web Statement of Rights, Licensor URL and Digital Source Type. A field an image lacks is left out, and no value or list is empty. `IMAGE_RIGHTS_FIELDS` lists them in that order, `IMAGE_LICENCE_FIELDS` the five without Digital Source Type, and `IMAGE_RIGHTS_FIELD_NAMES` their names as IPTC writes them. `METADATA_SUMMARY` (`metadataSummary.ts`) says in a few words what an output keeps and removes, as `wio --help` says it. It imports nothing, so a browser bundle can import it as a value.

- **`readRights(bytes, format)`** fills each field from the first carrier that has it:
  - XMP: JPEG's `APP1` (not Extended XMP), a PNG `iTXt`, `zTXt` or `tEXt` chunk keyed `XML:com.adobe.xmp`, the WebP `XMP ` chunk, or an AVIF `mime` item of type `application/rdf+xml`;
  - then IPTC IIM: JPEG `APP13` `Photoshop 3.0` segments, joined, 8BIM resource 0x0404, datasets 2:80, 2:110 and 2:116, in UTF-8 when 1:90 declares it and Latin-1 otherwise;
  - then EXIF IFD0's `Artist` and `Copyright`, in UTF-8 when valid and Latin-1 otherwise, where a `Copyright` of `photographer\0editor` gives both, joined with a space;
  - then PNG's `Author` and `Copyright` text.
  - Values lose the characters XML 1.0 can't hold, nulls included, so they read as the packet holds them. They are trimmed, and empty ones dropped. It never throws: a file whose structure can't be read gives nothing, since the strip reports it.
- **XMP** is parsed with `sax` (strict, with namespaces), never a regex. Properties match by namespace URI, never by prefix. A simple value comes from an attribute or an element, an array from any RDF container or a lone value, and a Licensor URL from any form of structure (`rdf:parseType="Resource"`, a nested `rdf:Description`, or attributes on the `rdf:li`). A malformed packet contributes nothing.
- **`mergeRights(fromFile, added)`** fills only the fields the file lacks, in `ImageRights`' order.
- **`buildRightsPacket(rights)`** builds the smallest valid packet: the `xpacket` wrapper with no padding, and one `rdf:Description` declaring only the namespaces it uses, with the simple fields as attributes, Creator as an `rdf:Seq`, Copyright Notice as an `rdf:Alt`, and Licensor as an `rdf:Bag` of `rdf:parseType="Resource"` items. Values are escaped, with tab, LF and CR as character references, since a parser turns them into spaces in an attribute and a CR into LF anywhere, and characters XML 1.0 can't hold are dropped. Rights with no fields give no packet.
- **`setRights(bytes, format, packet)`** replaces whatever XMP an encoded JPEG, PNG, WebP or AVIF has with the packet, or removes it when the packet is `undefined`, and applying the same packet twice changes nothing. For JPEG, PNG and WebP it edits only the XMP's byte ranges, through `spliceBytes`, so every other byte stays as it was. XMP is written by hand rather than with sharp's `withXmp`, which puts PNG XMP in a compressed `zTXt` chunk.
  - **JPEG:** one `APP1` segment after the last `APP0` or EXIF `APP1`, or straight after `SOI`, as the XMP spec orders them. Extended XMP is dropped too, since it belongs to the packet it extends. A packet over 65,504 bytes doesn't fit in one segment, and throws a `RangeError`.
  - **PNG:** one uncompressed `iTXt` keyed `XML:com.adobe.xmp` before the first `IDAT`, replacing every XMP text chunk.
  - **WebP:** an `XMP ` chunk at the end of the RIFF payload, with the `VP8X` XMP flag and the RIFF size updated. A simple WebP (a lone `VP8 ` or `VP8L`) given a packet first gains a `VP8X`. Its canvas size, and for `VP8L` its alpha flag, come from the bitstream header, since libwebp refuses a canvas that doesn't match the image. Removing the packet clears the flag but keeps the `VP8X`.
  - **AVIF:** every XMP item goes first, through `removeAvifItems`. A packet then becomes one `mime` item, byte for byte as sharp's `withXmp` writes it: an `infe` after the others (version 2, hidden, with an empty name and content encoding), a `cdsc` reference to the primary item at the end of `iref` (created when there's none), an `iloc` entry, and the packet at the end of the last `mdat`, or in a new `mdat` when all the data is in `idat`. Its ID is one above every item's and entity group's (`grpl`), which share one space. Its offset goes in the base offset when `iloc` has that field (libheif's layout), or else in the extent (libavif's). `meta` is built twice, to measure how much it grows, then with every file offset after it moved by that, and any after the packet by the packet's length. The image items, their properties and their data are untouched.
  - The packet goes in `mdat` with a file offset, as libheif and libavif write metadata, rather than in `idat`, which would need `iloc` version 1 and cost about 12 more bytes.
  - A file with no `SOS`, no `IDAT`, a chunk past the RIFF payload, a damaged simple WebP header, or a truncated AVIF box or item table fails with `E_DECODE`, as does an AVIF given a packet with no primary item for it to describe. An AVIF whose `iloc` has no field for the packet's offset or length throws a `RangeError`.

## SVG

`src/svg/` never rasterises an SVG. `docs/svg.md` is the user-facing account and lists what the render check can't see.

- `optimiseSvg` runs SVGO's `preset-default` with `multipass`, overriding `cleanupIds`, `inlineStyles` (it deletes the IDs and classes whose rules it inlines) and `removeDesc` to off, and `removeUnknownsAndDefaults` to `keepRoleAttr: true`. SVGO 4's preset already leaves `viewBox` and `<title>` alone. Recheck the preset's contents whenever SVGO is bumped.
- It tries `floatPrecision` 2, 3, 4 and 5, and returns the first whose renders score at least 90 (`SVG_TARGET`, whatever the raster target) at 1x and 2x. The scale is raised so the short side is at least 64 px, and capped at the scorer's 26 MP. Renders come from `decodeForScoring(bytes, { density })`, where 72 DPI is one pixel per SVG unit. A candidate that fails to render, or renders at a different size, fails.
- When no precision passes, it returns `stripSvg`'s output with `method: "strip"` and a score of 100. `stripSvg` runs only `removeComments`, `removeMetadata` and `removeEditorsNSData`, reports `comment` and `editor` from `inspectSvg`, and returns the input itself when there is nothing to remove.
- `gzipBytes` is `gzipSync` at level 9.

## Encoding and search

- The encoders in `src/encode/` take the source decoded by `decodeForScoring` (8-bit sRGB RGBA, orientation applied), never the file. The source is decoded once, and every candidate starts from the pixels it is scored against. A 16-bit source therefore reaches `pngLossless` as 8-bit, which the score confirms is invisible.
- `createPipeline` drops an alpha channel whose pixels are all opaque, so AVIF, WebP and PNG don't store one. Outputs carry no metadata and no ICC profile, since the pixels are already sRGB.
- The settings are hard-coded, with no user-facing effort flags: WebP effort 6, `smartSubsample`, `alphaQuality: 100`; lossless WebP quality 100, which libwebp reads as compression effort (sharp's default is 80); JPEG uses mozjpeg's defaults; lossless PNG uses compression level 9 with adaptive filtering, and palette PNG (`pngPalette`, method `lossy`, since the contract's `method` is a closed enum) libimagequant effort 7 with dithering 1.0 at compression level 9. AVIF effort 6 with `tune: iq`, WebP `smartDeblock` and the palette settings come from `node scripts/bench-encoders.mjs` (`--only` runs the configs whose names start with a prefix), and `docs/encoding.md` records the numbers. Re-run the benchmark after bumping sharp.
- `optimiseFile` sets `sharp.concurrency(1)` for the process. With more threads, libaom splits an AVIF into tiles, which made AVIFs 2 to 35% larger at the same target (9% on a photo) and made their bytes depend on the CPU count. WebP, JPEG and PNG don't change with threads. Batches get their parallelism from child processes instead, and the benchmark pins the same setting.
- `assertFitsFormat` refuses a side over 16383 px for WebP, 16384 for AVIF (sharp's HEIF limit) and 65500 for JPEG (libjpeg's) with `E_TOO_LARGE_FOR_FORMAT`, so the pipeline can drop that format's candidates and keep the others.
- `QUALITY_RANGES` holds the qualities searched per lossy encoder: WebP 30–95, AVIF 20–90, JPEG 40–95, palette PNG 1–100.
- `searchQuality` is pure; the encoder and scorer are passed in. It tries the highest quality first and stops if that fails. Otherwise it binary-searches for the lowest passing integer quality, then tries one step above it, because encoders aren't strictly monotonic. Each quality is encoded once. The chosen attempt is the smallest passing one, or the highest-scoring one when none passes (`reached: false`).
- **Running ahead:** given `lookahead`, which it reads at each step, `searchQuality` starts the qualities it could need next while it waits for the one it needs, breadth first over both outcomes and then theirs, up to that many unfinished, following only its own outcome below an attempt that has finished, ahead of need or not. It drops an attempt, aborting the signal in the attempt's context, once it can no longer reach it, and drops those left over when it's done. The context's `speculative()` is true until the search reaches the attempt. It still steps exactly as it would one at a time, and chooses from and returns only that path's attempts, so the result is the same for any scorer, which `tests/search/searchQuality.test.ts` checks against random scores in every range. Its `signal` stops it starting attempts.

## Pipeline

`optimiseFile` in `src/pipeline/` is the per-file entry point. `docs/modes.md` is the user-facing account of its rules.

- **Order:** read (`E_READ`), `inspect`, check the mode's primary output paths, decode (shrinking to `maxWidth`) and strip the source once, choose, check every chosen path, then write. The primary paths are the requested formats' (AVIF and WebP in `suite`), so a re-run skips finished files before any encoding. The strip fallback's and a suite fallback's paths are only known once chosen.
- **Candidates** (`rasterCandidates.ts`) hold no XMP, and are made per format: the strip when the source is already in that format, plus that format's re-encodes (PNG's are lossless and, when scorable, a palette search, which covers `same` for PNG inputs and every suite fallback), which run concurrently so sharp encodes in the background while the main thread scores, or, given a score pool (`optimiseFile`'s `scorePool`, which `createRasterSource` puts on the source), while the pool's threads score side by side. Each search runs ahead (see Encoding and search) on the pool's spare scorers: `lookaheadFor` gives each search the source is running (`searches.running`) the pool's scorers left once each has one for the attempt it needs, or two for an image with transparency, scored on two backgrounds, split evenly. It is read at each step, so in `suite` the AVIF search, which finishes last, gets them all once the others are done. Without a pool, a search doesn't run ahead. A search counts itself, then waits a turn of the microtask queue before its first step, so the searches a selection starts together all count before any runs ahead. A tiny image gets lossless encoders only. A PNG source adds lossless WebP and a near-lossless search over levels 20 to 80 (libwebp only tells levels 20 apart). A lossless WebP source stays lossless. `E_TOO_LARGE_FOR_FORMAT` empties that format's list instead of failing the file.
- **Max width:** `createRasterSource` shrinks a decoded source wider than `maxWidth` (the displayed width, since `decodeForScoring` has applied orientation) to exactly that width through `fitToWidth`, with the height rounded, through sharp's default Lanczos 3 on the raw RGBA, which premultiplies alpha. The app API's diff maps shrink an original through it too. Every candidate encodes from and scores against the shrunk pixels, so a score measures the encoding, not the resize. A strip keeps the old size, so a resized source's `strip` is `undefined`: `selectSingle`'s conversion falls back to the smallest passing re-encode in the input's own format, `suite` loses its unchanged-input fallback (the bound starts at the input's size), and `selectRaster` adds `W_NOT_RESIZED` when nothing is chosen. Each output carries the source's `width` and `height`.
- **Rights** (`sourceRights.ts`): `createRasterSource` reads nothing new, since `inspect` has read the input's `rights`. `createSourceRights` merges the `rights` option's fields into them and builds the tiers an output may carry, most first, each with its packet built once: the merged fields, the input's own when fields were added, then none. The last is left out when the input is its own strip carrying its rights, so rights are only dropped to remove other metadata (the user's decision). `stripAll` gives only none. The first tier comes from `wantedRights`. `withRights` writes a tier into a candidate through `setRights`, and a `RangeError` (a JPEG packet over one segment, an AVIF item table with no room) drops that candidate from the tier. `rightsWarnings` adds `W_RIGHTS_NOT_ADDED` when an output, or the kept original, lacks a field of the first tier, and otherwise `W_NO_RIGHTS` when that tier has no licence field and `stripAll` is off. `applyRights` writes the first tier into an output that may already carry XMP, for the app API's `/api/rights`. It drops nothing to keep the output smaller than its input, only the fields the format can't hold, as a run's tiers do: the added ones, then the file's own.
- **Selection** (`selectRaster.ts`) keeps candidates smaller than a bound and picks the smallest that reaches the target, with their rights written in (`pickCandidate`). `same`, `webp` and `avif` try each tier in turn as a whole pass, the requested format then the strip fallback, and take the first that chooses something. Only `webp` and `avif` modes converting to another format may fall back to the highest-scoring candidate below the target (`W_TARGET_NOT_REACHED`).
- **Suite:** `selectSuite` searches every format at once, and picks each role's output with `pickCarrying`: the smallest reaching the target below the input's size (`suiteBound`, plus one for the fallback, so a JPEG or PNG input with nothing to strip is its own fallback, unchanged, and a page always has one), carrying the first tier with which one does. It then applies the chain rule, `keptBySuiteChain` (`suiteChain.ts`, which imports nothing, so the UI can bundle it): the fallback, then WebP, then AVIF, each kept only when smaller than the last one kept. Fields are never dropped to beat the chain.
- **One format:** `selectFormat` picks a format's output as `suite` picks a role's, without the chain, for the app's target sliders. When nothing reaches the target below the input's size, it takes the best carrying the first tier that leaves one, which may fall short of the target or be larger than the input. It throws `E_TOO_LARGE_FOR_FORMAT` or `E_TOO_SMALL_TO_SCORE` when the format has no candidate.
- **Kept-original** is any selection whose outputs are all byte-identical to the input, including none.
- **Destinations** (`destination.ts`): an output is named after the input, keeping the input's extension when it fits the format. A path is the input when its device and inode match, which sees through case, links and `..`; where the file system reports no inode, the resolved paths are compared, case-insensitively on Windows and macOS. An unchanged output at the input's own path is neither written nor a clash.
- **Writes** (`writeOutputs.ts`) go to `.<name>.wio-<hex>.tmp` in the destination folder, and are renamed only once all of a file's outputs are written. Temp files are removed in `finally`, and any failure except an abort becomes `E_WRITE`.

## CI

`.github/workflows/ci.yml` runs on pull requests, pushes to `main` and manual runs. `scripts/ci-scope.mjs` decides what each run needs:

- **Every run** lints, builds and runs `npm run test:fast` on Ubuntu, Windows, macOS arm64 and macOS Intel with Node 24, and on Ubuntu with Node 26.
- **A pull request that changes engine files** (`src/`, `wasm/`, `fixtures/`, `tests/golden/`, `package.json` or the lockfile) also runs `npm run test:golden` on Ubuntu.
- **A pull request that changes the desktop app's files** (`desktop/`, `ui/`, `src/app/`, `tests/desktop/`, `package.json` or the lockfile) also runs the desktop job on Ubuntu: `npm run build:desktop`, then `npm run test:desktop` under `xvfb-run`. It fetches Electron's binary in a step of its own, and sets `kernel.apparmor_restrict_unprivileged_userns` to 0, since Ubuntu 24.04's AppArmor otherwise refuses Chromium's sandbox the user namespaces it needs, and the test runs with the sandbox on.
- **A release pull request**, one that changes the version in `package.json`, runs the golden tests on every OS and the desktop job, and `scripts/check-release.mjs` checks that the version is higher than the base branch's, the lockfile matches it, and `CHANGELOG.md` has a `## <version>` heading.
- **A manual run** (`gh workflow run ci.yml --ref <branch>`) runs the golden tests on every OS and the desktop job, for a change that needs checking on every platform before its release.
- **A push to `main`** runs only the fast checks, because its pull request already ran the rest.
- **Desktop releases** (`.github/workflows/desktop.yml`): a `desktop-v<version>` tag, which must name `package.json`'s version, builds the installers on Windows, macOS arm64 and macOS Intel, each on its own runner so sharp installs that platform's binaries. Each runs `npm run test:desktop` against its packaged app, and one job, the only one that can write, attaches the installers to a draft GitHub release.
- **Concurrency:** a newer run cancels an older one for the same ref and event, so a second push supersedes the first, but a manual run doesn't cancel the push run before it. A cancelled job fails "CI passed".
- **"CI passed"** needs every other job, and passes when each one passed or wasn't needed. It's the one check to require: a skipped job counts as passing for a required check, so the individual jobs must not be required.

## Golden tests

`tests/golden/` is the engine contract. `goldenMatrix.ts` runs every fixture through every mode with `optimiseFile`, checks every rule the pipeline promises (sizes, metadata, dimensions, alpha, warnings, the suite chain, the JSON contract, a recomputed score), and compares each result with `golden.json`: status, error and warning codes, roles, formats and methods exactly, quality within 3, size within 10%.

- Each mode is split into four shard files, `<mode>.<n>.test.ts`, with the fixtures sorted largest first and dealt out in turn, so each shard gets one photo and Vitest runs them in parallel.
- `node scripts/update-golden.mjs` regenerates `golden.json` from the build, running `optimiseBatch` in child processes in a dry run. The tests never write it. Changing it is an API change; the `update-image-engine` skill covers the process.
- With threads pinned, every golden result was byte-identical on Windows x64 and Linux x64, and on a subset of nine fixtures in every mode under emulated Linux arm64. Before pinning, only AVIF differed, because of the thread count. macOS hasn't been compared directly; CI runs the golden tests there, and the tolerances allow for small platform differences.

## SSIMULACRA 2 module

- `wasm/` is a Rust crate wrapping the `ssimulacra2` crate. Its build output, `wasm/pkg`, is committed so contributors need no Rust. Only `npm run build:wasm` writes it; never hand-edit it. The Dockerfile pins the base image by digest and wasm-pack, wasm-bindgen and wasm-opt by checksum, and runs wasm-pack with `--mode no-install` so nothing is downloaded unverified. CI rebuilds it on every change under `wasm/` and fails if the output differs.
- The WASM `score(reference, distorted, width, height)` takes 8-bit sRGB RGB pixels with no alpha. It throws on a buffer-length mismatch or images under 8x8. Only `src/metrics/` calls it.
- The generated JS is CommonJS (`wasm/pkg/package.json` sets `"type": "commonjs"`) and compiles the module synchronously on first `require`. `src/metrics/ssimulacra2.ts` is the only loader: it requires the module lazily through `createRequire` on the first score, from `dist/wasm` (which `npm run build` copies from `wasm/pkg`) when compiled, or from `wasm/pkg` when running TypeScript source under the tests, which `isSourceRun` (`src/runtime/`) tells from its `import.meta.url`. `tests/dist.test.ts` checks the compiled path whenever `dist/` exists, which it always does in CI.
- WASM memory is capped at 4 GiB (wasm32), grows to fit the largest pair scored and never shrinks: about 2 GB for a 12 MP pair and 4 GiB for 26 MP. A 27 MP pair still fits and a 28 MP pair traps. A trap leaves the instance unusable, so the loader discards it and the next score loads a fresh one. Every thread that scores has its own instance, so a score pool's threads each grow their own, until the pool ends an idle one (see Metrics).
- Scores match libjxl's reference `ssimulacra2` tool within 0.5 (0.104 at most on the pairs in `fixtures/ssimulacra2/`), and a test holds them to it.
- Speed, from `node wasm/bench.mjs` on an i9-10850K with Node 24: one score takes about 1.1 s at 1 MP and 13.3 s at 12 MP (1.9 GiB RSS). libjxl's native tool takes about 0.19 s and 1.8 s. A score runs on one thread and can't be split, and async concurrency alone would queue every score on the main thread, so scoring in parallel needs more threads: batch lanes use child processes, and within one, a score pool's worker threads score one file's candidates side by side. Each keeps its WASM memory, so memory limits the lanes and the pools as much as CPU count. A pool of 4 took a `suite` run of a 12 MP photo from 412 s to 330 s, with the same outputs. More threads help only once searches run ahead (see Encoding and search), since otherwise the AVIF search's attempts, each a 20 s encode and a 13 s score, set the pace one after another: on a pool of 9, running ahead took that run from 330 s to 200 s, and a WebP search of the photo from 130 s to 67 s (63 s on a pool of 4). libuv's 4 threads then held the encodes back, as a needed attempt's decode waited behind the encodes ahead of it, so a child's libuv pool is sized for its scorers (see Batches): in a session that ran about 10% slower, the WebP search on 9 took 75 s with 4 libuv threads, 61 s with 9, 57 s with 13, the size it now gets, and 56 s with 18.

## Metrics

`src/metrics/` is the only code that compares pixels. Every comparison goes through `decodeForScoring`, which applies EXIF orientation and converts to 8-bit sRGB RGBA, so a candidate is always scored against the decoded source.

- Every public function checks that each buffer holds `width * height` RGBA pixels and that the two images share their dimensions, throwing a `RangeError` otherwise.
- `score` is async. It composites images with transparency onto black and onto white, in sRGB like a browser, and returns the lower score. An opaque pair is scored once.
- **Score pool** (`scorePool.ts`): `createScorePool(size)` starts up to `size` `worker_threads` as pairs need them, each running `scoreWorker.ts`, which scores through `ssimulacra2.ts`, so a trap discards only that thread's instance. Given one, `score` sends each background's pair to it at once and awaits them, so its thread stays free for other searches' encodes and scores; without one it scores on the calling thread, one background at a time, so only one pair's pixels are held, which is what runs from the TypeScript sources, since a thread can't load `.ts` files through their `.js` imports. Scores are bit-identical either way. Pairs run in arrival order, except that a pair whose `speculative()` returns true waits behind every pair whose doesn't. It is read each time a thread frees, so a pair a search reaches while it waits takes its turn among the needed ones. `signal` drops a pair still waiting, rejecting with its reason, while one being scored finishes, as a WASM call can't be interrupted. `flatten` gives each pair memory of its own (`allocUnsafeSlow`, never the shared pool's), which the thread takes rather than copies; a pair resized for scoring is copied, since sharp's memory can't be transferred. A thread that exits fails its pair and is replaced for the pairs waiting, a pair no thread can start for (`new Worker` throws when the OS has none) fails, idle threads are unref'd so they don't keep the process alive, and `close` terminates them, failing the pairs waiting or being scored. A thread idle for `idleMs` (30 s) leaves the pool, so no pair is posted to it while it stops, and is terminated, freeing its WASM memory. One started in its place spends about 15% longer on its first score, compiling the WASM and growing its memory: 0.2 s more at 1 MP, 1.6 s at 12 MP. `tests/metrics/scorePool.test.ts` runs a stand-in thread, `fakeScoreWorker.mjs`, which loads under the sources, and `tests/dist.test.ts` scores `fixtures/ssimulacra2/`'s pairs through a pool of the build's.
- Identical pixels score 100 without flattening or calling the WASM. Lossless candidates therefore cost almost nothing to score, and they score even when the image is below the 8x8 minimum. A differing pair under 8x8 throws, so callers check `isScorable` first.
- A pair over 26 MP is resized (sharp's default Lanczos 3) to 26 MP at the same aspect ratio and scored at that size, the most the WASM memory holds. That slightly overstates quality, so callers check `isDownscaledForScoring` and warn that the score is approximate. This applies to the CLI and the UI alike.
- `verdictFor` maps a score onto the SSIMULACRA 2 README's bands. Each band includes its lower edge.
- `createDiffMap` amplifies the luma difference 8 times and draws it from red to yellow over the reference, greyscaled and dimmed to half brightness. For images with transparency it also compares the black composites and draws the larger difference.

## Batches

`optimiseBatch` runs files in lanes, as many as `concurrency`, each taking the next file from a shared queue. Its body is `runBatch` (`runBatch.ts`), which takes a function that names the files failing before any work, so the app API can share it: `optimiseBatch` passes its output conflicts.

- **Processes:** each lane owns one child process (`worker.ts`, forked by `createProcessExecutor`), because scoring blocks its thread, and because libuv's pool, which queues every sharp encode and decode and every fs call, is per process. With worker threads, nine lanes shared one pool of 4 threads, and 9 AVIF photos took 270 s; in child processes they take 140 s, and a suite run of them 172 s (i9-10850K, 9 lanes). Each child's libuv pool has half as many threads again as its scorers, and at least libuv's 4 (`libuvThreads`, in `concurrency.ts`), since a search running ahead keeps about as many attempts in flight as its scorers, each an encode, then a decode, there. It can only be set at spawn, as `UV_THREADPOOL_SIZE`, since libuv reads it once. A native crash in libvips or libheif fails one file with `E_INTERNAL` rather than the run. The TypeScript sources (`isSourceRun`) run lanes on the calling thread instead, since a child can't load `.ts` files through their `.js` imports, so the tests cover the process path through the built package in `tests/dist.test.ts`. `runFile` (`executors.ts`) is shared by both, and turns a non-`OptimiserError` rejection into an `E_INTERNAL` result.
- **Slots:** `processSlot.ts` holds the lifecycle that the app API's pixel runner shares. It forks with `serialization: "advanced"`, `execArgv: []` and stdout ignored, since stdout carries the JSON contract, and, given a libuv thread count, with the parent's environment plus `UV_THREADPOOL_SIZE` set to it, which a replacement gets too. It answers one message at a time, starts the child when first needed and replaces it after a crash. `send` never rejects: it resolves `crashed` on the child's `exit` or `error`, and a `disconnect` kills the child so the `exit` that follows reports its code. Listeners are attached once for the child's life, since an unhandled `error` throws in the parent. `close` disconnects, sends SIGKILL and waits for `exit`. The children ignore SIGINT and SIGTERM, because a terminal's Ctrl+C reaches the whole process group and the parent's abort message must be what stops a lane, so it finishes its step and removes its temp files. They exit on `disconnect`, so a killed parent leaves no orphans. Each child installs these handlers before it loads the engine with `await import()`, which can take seconds on a busy machine, since Node holds the parent's messages until the `message` listener is added. A signal in the moment Node itself starts still kills a child, and its file ends as `E_INTERNAL` in a run that is stopping anyway.
- **Concurrency** is how many scores run at once, and defaults to one fewer than `availableParallelism()`, capped at one per 4 GiB of `totalmem()`, a scorer's WASM ceiling (`defaultConcurrency`, in `concurrency.ts`). `laneScorers` splits it over `min(concurrency, files)` lanes, evenly, the first lanes taking one more when it doesn't divide. Each lane's child gets its share as its argument (`createProcessSlot`'s `args`, never the environment) and scores on a pool of that many threads when it's more than 1, kept for the child's life. So a batch of at least as many files as the concurrency runs as before, each lane scoring on its own thread, and a smaller one scores each file's candidates side by side, with no more scorers, and so no more WASM memory, than the budget. The sources' in-process lanes ignore their share, since a thread can't load `.ts` files. On an i9-10850K, whose default is 9, 9 AVIF photos took 130 s at target 70, a lane per file as before, and a `suite` run of one 12 MP photo took 464 s on one scorer, 241 s on 4 and 194 s on 9, with the same outputs, its searches running ahead (373 s on 4 or on 9 before they did). Sizing each child's libuv pool for its scorers (see Processes) then took that run to 167 s on 9 and 227 s on 4, against 209 s and 239 s with libuv's 4 threads in the same session, while the AVIF photos, whose lanes keep 4, took 119 s.
- **Conflicts:** before any work, the batch reads each input's first 16 KB in turn, one file at a time, and detects its format (`sniffFormat`, in `src/inspect/`, which the app API's `open` shares). `outputClaims` (in `destination.ts`) lists every path its outputs could take, named by `outputPath` itself: the requested formats, a suite's JPEG and PNG fallbacks, and the input's own format. An input fails with `E_OUTPUT_CONFLICT` when a claim is another input's path, or already claimed by an earlier input, or when it repeats an earlier input. An unreadable or unsupported file claims nothing and fails in its own turn.
- **Aborting:** one `AbortController` links the caller's signal and any lane's failure, such as `onEvent` throwing. The batch waits for every lane with `Promise.allSettled`, so it only rejects once every file in progress has cleaned up, and each lane's `finally` closes its child. An aborted batch emits no `run-done`.

## JSON contract

`src/schema/contract.ts` holds the zod schemas for `RunResult`, `FileResult`, the events and `CompareResult`, and `src/pipeline/types.ts` and `src/compare/types.ts` derive the public types from them with `z.infer`. zod takes about 60 ms to import, so no module the CLI loads imports `contract.ts`; only the tests and the app API do. Tests check a result with `expect(schema.parse(result)).toEqual(result)`, since parsing strips any field the schema lacks. Enums the contract shares with other modules are `as const` tuples there, such as `INSPECT_FORMATS`, `METRICS_VERDICTS`, `STRIP_REMOVED_KINDS`, `ENCODE_METHODS` and `IMAGE_RIGHTS_FIELDS`.

## Comparisons

`compareFiles` (`src/compare/`) is what `wio compare` runs. It reads and inspects each image with `readInput` and `inspect` (refusing SVG), checks their dimensions, checks the diff map's path against both images with `planWrites`, scores them with `decodeForScoring` and `score`, and writes `createDiffMap`'s PNG through `writeOutputs`. As in `optimiseFile`, an `OptimiserError` becomes the result's `error`, its message prefixed with the image's path. The result's schema is `compareResultSchema`.

## CLI

`src/bin/` builds a `CliIo` from the process: the streams, colour from `stdout.hasColors(process.env)` (off for `NO_COLOR`), progress when stderr is a terminal, and an `AbortSignal` for Ctrl+C and SIGTERM. It passes that to `runCli` in `src/cli/`, which returns the exit code, so the tests run the whole CLI in-process. `docs/cli.md` is the user-facing account.

- **Program:** commander. `defineOptimise` puts the optimise arguments, flags and action on both the program itself, so `wio <inputs>` needs no command name, and its `optimise` (alias `optimize`) subcommand. `enablePositionalOptions` stops the program taking `compare`'s `--json` as its own. `exitOverride` turns every usage error into a `CommanderError`, which `runCli` maps to exit 2, and help and `--version` to 0. An action reports its own usage errors, such as `E_NO_INPUTS`, through `command.error`, so they print the same way. Flag values go through parsers that throw commander's `InvalidArgumentError`, making the engine's checks (`isWebUrl` for the rights URLs) usage errors rather than its `RangeError`s. The rights flags' attribute names are `PipelineRightsOptions`' keys, and `--strip-all` `conflicts()` with them.
- **Help** is fixed at 80 columns (`HELP_WIDTH`), so it reads the same in a terminal and piped. `configureHelp` sets commander's width, leaves `[options]` out of the command list so the option column has room to wrap, and shows each option's description alone, so a description states its own default and choices. The sections after the options are built with `wrapHelp` and `helpList`, and the Metadata section from `METADATA_SUMMARY`.
- **Inputs** (`expandInputs.ts`): a path that exists is taken as it is. A folder is scanned by extension with tinyglobby (subfolders with `--recursive`), leaving out an `--out-dir` inside it. An argument that doesn't exist but has glob characters is globbed, with `\` turned into `/` on Windows and matching case-insensitively on Windows and macOS. A pattern matching no image is passed on as a path, so it fails with `E_READ`. Scanned files get their subfolder, mirrored under `--out-dir`, as their own `outDir`: below the folder, or below a pattern's fixed start, `picomatch.scan`'s `base` (a brace group can hold a `/`), where a match above it goes straight into `--out-dir`. A scan leaves out a file in the mode's WebP or AVIF format named as another input's output beside it, taking it for an earlier run's output. Inputs are de-duplicated and sorted by `comparablePath`.
- **Output:** results go to stdout (`renderRun`'s table, `--json` or `--ndjson`), and everything else to stderr. `withHint` appends the flags that fix `E_OUTPUT_IS_INPUT`, `W_OUTPUT_EXISTS` or `W_NO_RIGHTS` (`OPTIMISE_HINTS` in `hints.ts`) to its message, in the JSON too, because the engine's messages don't name CLI flags. `renderRun`'s table leaves `W_NO_RIGHTS` off each file and counts it in one line for the run, since a batch without rights would repeat it on every row; `--json` and `--ndjson` keep it per file. The wording the UI shares, such as sizes, quality, totals and verdict meanings, lives in `format.ts`, which imports only types so the browser can bundle it; `paint.ts` adds the terminal colours.
- **Signals:** the first Ctrl+C or SIGTERM aborts the batch, which rejects once the files in progress have cleaned up, and `src/bin/` then exits with 128 plus the signal's number. The lanes' child processes ignore the signal, which a terminal sends the whole process group, and stop through the batch's abort. A second signal calls `process.exit` at once, and the children exit when their channel closes. An `EPIPE` on stdout or stderr, whose reader has gone (`head`), aborts the same way and exits 141 (128 plus SIGPIPE's number on POSIX, hard-coded since Windows has none); its listener stays for the process's life, since the error can arrive after `runCli` has returned, which then keeps its exit code. `tests/bin/wio.test.ts` checks it by closing the child's stdout at once.
- **Tests:** `tests/cli/` runs `runCli` in-process with captured streams. `tests/bin/wio.test.ts` spawns the built `dist/bin/index.js` (it is skipped without `dist/`), runs `SKILL.md`'s commands as written, and on POSIX checks that Ctrl+C exits 130 leaving no temp files.
- **`SKILL.md`**, at the root, is the agent guide, which a project copies into its skills. Keep its commands runnable, since the end-to-end test runs them.

## App API

`createAppApi()` (`src/app/`) is the API the desktop app talks to. It returns `{ handle, open, savePath, saveFolder, saveOutput, saveSuites, close }`. `handle`, which the page reaches, takes a web `Request` and resolves with a `Response`, and never rejects, so the routes are plain `(request) => Response` functions keyed by method and path (`findRoute.ts`), with no web framework and no network port. The other calls are the main process's: they take the paths its OS dialogs chose. It is internal, like the page it serves, so it isn't part of the JSON contract, and only the desktop's main process and the tests import it. `src/app/index.ts` is main's one door into the engine: besides `createAppApi`, it exports what main needs, `APP_HEADERS`, `describeFailure`, `readAppOptions`, `toolVersions`, `EXTENSIONS`, `formatOfExtension` and `FORMAT_NAMES`.

- **Responses:** `describeFailure` turns an `ApiError` into its status with `{ error, code? }`, an `OptimiserError` into a 422 with its code, and anything else into a 500, and main uses it too, to describe a failed save to the page. A path with no route is a 404. Every response gets `APP_HEADERS` (`nosniff`, `no-referrer` and the page's CSP), which main's protocol handler also puts on the page's own files, and images get `Content-Security-Policy: sandbox`, so an SVG opened as a page can't run scripts. `parseRequest` needs `application/json` (415) and a body its zod schema accepts (400), and `resolveOptions` checks a run's or a search's options as a run would (400).
- **Opening** (`openedFiles.ts`): `open(paths)` takes each path's real path, and registers it when it is a file whose leading bytes are an image (`sniffFormat`), as `file/<n>/<name>`, numbered in the order opened. A path opened again, however it's written, gets its first ref. A path that isn't an image gets `{ name, error }` and no number, and `open` never rejects for one.
- **Refs:** `handle` never takes or gives an absolute path. A ref is an opened file's `file/<n>/<name>`, or `session/<path>` in the temp folder, with `/` separators (`refs.ts`). `resolveRef` takes the kinds a route allows, and refuses any other with 400. A `file/` ref is looked up in the registry, never joined into a path, and must still be a file that isn't a link (`lstat`), or 404. A `session/` ref refuses an empty, `.` or `..` part or a backslash with 400, then needs an image's extension and the real path to be a file inside the temp folder, or 404, which catches links. It returns that real path, so a link swapped after the check can't redirect the read. `resolveOutput` also needs a `session/` ref to be in `runs`, `searches` or `rights`, the outputs a save may take. `readImage` reads a file and refuses one whose bytes aren't an image with 404.
- **Temp folder:** a `mkdtemp` named `.wio-app-*`, hidden so a scan above it skips it. Runs go to `runs/<n>/<input index>/`, searches to `searches/<n>/`, `/api/rights` to `rights/<n>/<index>/` and diff maps to `diffs/<n>/diff.png`. `close` answers any later request with 503 and rejects any later call, aborts a run, closes the pixel runner (which fails the jobs still queued rather than start a child), waits for every request and call in progress and the run's cleanup, and removes the folder.
- **Runs:** `POST /api/optimise` takes opened files and runs `runBatch` in `suite` mode at the target given, with `maxWidth`, `stripAll` and `rights`, each input in an output folder of its own, so no two outputs clash and nothing is written beside the originals (the user's decision: a run in the app is a preview). A `file/` ref that names no opened image fails as its file with `E_READ`, as a missing file does on the command line, and any other ref is a 400. Paths in messages become refs in one pass of one pattern, over the file's own input and outputs. It streams the events as server-sent events, with refs in place of paths in fields and messages, and an `error` event if the run broke. One run goes at a time: a new request stops the one in progress and waits for its files to clean up, so Stop then Run can't race, and a closed stream or `close` aborts it.
- **Pixel jobs:** `POST /api/search` (an opened file's output in one format at a target, with `maxWidth`, `stripAll` and `rights`) and `/api/diff` run one at a time in a child process (`pixelWorker.ts`, through a process slot), because scoring blocks its thread, and in-process from the TypeScript sources, as batch lanes do. The child scores on a pool of as many threads as a run's default concurrency, passed as its argument, since it runs one job at a time, with a libuv pool sized for them, as a lane's is (see Batches). A search alone runs ahead on all but one of them, so a 12 MP photo's search grows the pool to the whole budget. Its threads start as pairs need them and end once idle for 30 s, freeing their WASM memory, so a run beside a search holds up to twice the budget's scorers only while both are working. A search builds its source with `createRasterSource` and chooses with `selectFormat`, so it resizes, searches and writes rights exactly as a run's suite would, apart from the chain rule, which the page applies with `keptBySuiteChain`. `reached` says whether it met the target, and a negative `saving` that it's larger than the original. A diff shrinks the original with `fitToWidth` to the `maxWidth` its candidate was made at, and the child keeps the last original it decoded. For its searches, the child keeps a `RasterCache` (`rasterCandidates.ts`) per file, version and `maxWidth`, for the three searched most recently, dropping any of an older version: the decoded pixels, and every candidate encoded and scored, keyed by encoder and quality. Attempts made ahead of need go into it too, and one dropped before it was scored fails, so the search that takes it from there makes it again. A search at another target, in any format, takes a quality an earlier one tried from there, so a slider move pays only for new qualities (a 12 MP photo's WebP went from 128 s to 74 s moving 70 to 75). The target and the rights stay out of it, since candidates carry no rights until selection writes them in, and encodes are deterministic with sharp's threads pinned, so a search gives what an uncached one would. Results are cached for the session by request, and failures aren't. Both caches include each file's `fileVersion` (its file ID, modification time and size), so a file replaced since is never served from an old result. A search reads the version before and after the file, and keeps nothing for later when they differ, since a save landed as it read. `/api/image` sends it as the `ETag`, answering 304 when it matches.
- **Rights:** `POST /api/rights` rewrites outputs' rights when the metadata options change, with no re-encode: each output through `applyRights`, from its original's own fields (`readRights`, once per original in a request) and the ones given. `larger` marks one the fields make larger than its original, which a save then refuses. An SVG comes back as it is.
- **Saving** (`save.ts`): `savePath` gives where a pane's save dialog starts, the original's folder with the output named as `outputPath` would, or the next free name, and `saveFolder` where Save suite's folder picker starts, the first original's folder. It and the save calls read the original by its `file/` ref and each output by `resolveOutput`, and refuse an output larger than its original (422). The save calls write through `planWrites` and `writeOutputs`. `saveOutput` needs an absolute path whose extension fits the output's format, and passes `inPlace` when the path is the original and `overwrite` otherwise, only with `replace` (409 without). `saveSuites` names each output as `outputPath` would in the folder, taking the next free name, and writes every file to a temp file before renaming any. An output that is its original, unchanged, at the original's own path keeps its name, and `planWrites` leaves it where it is, as in a run.
- **Free names** (`freeName.ts`): `nextFreeName` follows the host OS: `stem (n).ext` from 1 on Windows and Linux, counting on from a stem ending in ` (n)`, and Finder's `stem n.ext` from 2 on macOS, which never reads a count in the stem. `createFreeNames` reads a folder's names once, compares them NFC-normalised and, on Windows and macOS, ignoring case, and counts every name it hands out as taken.
- **API schemas** are zod schemas in `api.ts`, for the routes and for the main process's calls, whose refs come from the page and are checked with `parseValue`. `parseRequest` checks every JSON body, and the tests parse every response and result with them. The UI imports its types, so `api.ts` imports only schemas and constants, never an engine stage.
- **Tests:** `tests/app/` creates the API through `appSession.ts`, which opens fixtures copied into a temp folder, and hands it `wio://app/` requests, one file per module, plus `createAppApi.test.ts`, `createPixelRunner.test.ts` and `pixelJobs.test.ts` (a search cache's file versions and widths). `tests/dist.test.ts` covers the pixel process through the build.

- **Options:** `readAppOptions` reads the desktop's options bar from the page or from `state.json`, keeping each field a run takes (`isMaxWidth` and `rightsFieldError` from `resolveSettings.ts`, which `resolveSettings` uses too) and dropping the rest, so one bad field never loses the others.

## Desktop app

`desktop/` holds the Electron shell: its main process (`desktop/src/main/`), its preload (`desktop/src/preload/`) and the IPC channel names they share (`channels.ts`). There is no `desktop/package.json`: the root package is the Electron app, with `main` pointing at `desktop/build/main/index.js`, `productName` naming the user data folder, and `electron` a dev dependency, which downloads its binary the first time it's run rather than on install.

- **Engine:** main imports the app API as `#app`, a subpath import in the root `package.json` that Node resolves to `dist/app/index.js`, so it runs the root's build, and `tsconfig.test.json`'s `paths` maps it to `src/app/index.ts` for the type-check. sharp's native binaries load in Electron's main unchanged (they use Node-API), and the batch lanes and the pixel runner fork their child processes from it, which Electron runs as Node.
- **Build:** Vite bundles main (`desktop/vite.main.config.ts`, an SSR build into one ES module, leaving `electron` and `#app` external) and the preload (`desktop/vite.preload.config.ts`, one CommonJS file, since a sandboxed preload can only `require` Electron's own modules), and `ui/vite.config.ts` builds the page, all into `desktop/build/`, which is gitignored. Main isn't compiled with `tsc`, because its program would pull in the engine's sources through the bridge's types and emit them. ESLint and `npm run typecheck` cover `desktop/src/` through `tsconfig.test.json`.
- **Start** (`index.ts`): it enables the sandbox, registers `wio` as a privileged scheme (`standard`, `secure`, `supportFetchAPI`, `stream`) and takes the single-instance lock at the top level, then starts from `whenReady().then(...)`: Electron fires `ready` only once the entry module has run, so awaiting it at the top level never returns. It creates the app API, closes it on `before-quit` (which stops a run and removes the temp folder), and quits when the window closes, on macOS too, since the app is its one window. A second launch shows the running app's window, and hands it the files it names.
- **Opening from the OS** (`index.ts`'s `receiveFiles`, and `commandLineFiles.ts`): the files the OS hands the app arrive on its own command line (Windows' Open with, and a drop onto the exe or its shortcut), on a second launch's, which the single-instance lock sends as `second-instance` with its working folder, and through macOS's `open-file` (Open With, and a drop onto the Dock icon). The listeners are added before `ready`, which `open-file` can precede, and the files wait until the page has loaded, since `openPaths`, which takes them, shows the window, which waits to draw. `commandLineFiles` picks the files out of a command line: the arguments after the executable that aren't switches, less the app's own path when `electron .` started it (`process.defaultApp`), resolved against the working folder, keeping only existing files. It imports nothing from Electron, so `tests/desktop/main/` unit-tests it.
- **Protocol** (`appProtocol.ts`): `protocol.handle("wio")` passes `wio://app/api/*` to `handle`, whose streamed run events reach the page as they're written, and serves the renderer build's files for anything else, refusing a path that leaves it, with `APP_HEADERS`. In development, when `WIO_DEV_SERVER` is set and the app isn't packaged, it passes the page's requests to Vite instead, so the page keeps its origin, with a CSP that also allows Vite's inline scripts and its hot-reload socket.
- **Window** (`appWindow.ts`): one `BrowserWindow` with `contextIsolation` and `sandbox`, shown once it has drawn. Every page is guarded: it can't navigate off `wio://app`, open a window or attach a webview, web links open in the system's browser, and every permission request is refused.
- **Bridge** (`bridge.ts` and `preload/index.ts`, typed by `ui/src/desktop.d.ts`): the preload exposes `window.wio` through `contextBridge`, and each call is an `ipcRenderer.invoke` that main answers only from the window's main frame on `wio://app`. The file calls return an `outcome`: `opened`, `saved`, `canceled` when a dialog is dismissed, or `failed` with `describeFailure`'s body. Every path comes from an OS dialog or a drop: the preload reads a dropped file's path with `webUtils.getPathForFile`, which gives none for a file the page made. `openPaths` is the one way main opens files itself (the menu's Open..., and the files the OS hands the app): it opens them, remembers their folder and sends them to the page as `onFilesOpened`, holding them until the page subscribes, which the preload reports, both at first and after a reload. Subscriptions pass the callback the payload alone.
- **State** (`desktopState.ts`): `state.json` in the user data folder keeps the last folder images were opened from, which the open dialog starts in while it's still a folder, and the options bar's values, through `readAppOptions`. It is written whole, to a temp file then renamed, one write at a time, and a failed write only forgets a preference.
- **Menu** (`appMenu.ts`): File (Open..., Save All, and Quit or Close), Edit, View (reload and the developer tools only when not packaged) and Window, with About in the app menu on macOS and under Help elsewhere, showing the versions of wio, sharp and libvips. Save All sends the page `onMenuCommand("save-all")`, since only the page knows which images have finished.
- **Development** (`scripts/dev.mjs`): bundles main and the preload, serves `ui/` from Vite on 127.0.0.1:5173, with its hot-reload socket there too, and launches Electron without `ELECTRON_RUN_AS_NODE`, which an editor built on Electron, such as VS Code, can leave set, and which makes Electron run as plain Node.
- **Packaging** (`desktop/electron-builder.yml`, run by `npm run package:desktop`): electron-builder packs `package.json`, `dist/` and `desktop/build/{main,preload,renderer}`, with the production dependencies, into `app.asar`. It unpacks only sharp's and `@img`'s native binaries, which load only from real files: Electron's Node mode reads the archive, so the batch lanes and the pixel runner fork their scripts from inside it, and the WASM and a score pool's threads load from there too. `npmRebuild` is off, since sharp uses Node-API, and `publish: null` writes no update files. The `RunAsNode` fuse stays on, as `fork` needs it. Windows gets a per-user NSIS installer, and macOS a `.dmg` per architecture, ad-hoc signed (`identity: "-"`, since Apple silicon runs no unsigned code) and without the hardened runtime, which would refuse its ad-hoc signed libraries. Both register the five input formats for Open with, without becoming any format's default: macOS's through `mac.fileAssociations`, as a `Viewer` ranked `Alternate`, and Windows' through `desktop/resources/installer.nsh`, whose `customInstall` lists a ProgID of the app's own (`<appId>.<ext>`) in each extension's `OpenWithProgids`, and whose `customUnInstall` removes them. electron-builder's own `fileAssociations` would also set each extension's default on Windows, and leave it naming a removed ProgID after an uninstall.
- **Icons:** `desktop/resources/` holds the outline in one colour (`currentColor`) as `icon.svg` and, for 16 and 24 px, the simplified `icon-small.svg`. `scripts/build-icons.mjs` renders them in white on the app-blue tile into `desktop/build/icons/`: `icon.png`, 1024 px with the tile on macOS's 824 px grid, from which electron-builder makes the `.icns`, and `icon.ico`, with bitmaps from 16 to 128 px and a PNG at 256. The page's header masks `icon-small.svg` with `--primary`.
- **Tests** (`tests/desktop/app.test.ts`, run by `npm run test:desktop` and left out of `npm test` and `test:fast`): it drives the built app, failing when `npm run build:desktop` hasn't made it, or the packaged app whose executable `WIO_DESKTOP_APP` names, with `playwright-core`'s `_electron.launch`, in a temp user data folder (`--user-data-dir`) and without `ELECTRON_RUN_AS_NODE` or `WIO_DEV_SERVER`. It keeps Chromium's sandbox on (`chromiumSandbox`, which Playwright turns off on Linux otherwise). The OS dialogs are stubbed in main through `evaluate`, and the menu is clicked there too. Its tests run in order, each carrying on from the last: opening, a slider's search, the wipe, saving under a free name, Save all and the menu's, the width, Help, rights making a pane larger, rights written and removed on a save, a relaunch keeping the folder and options, a launch naming an image and a second launch naming another from its own folder, and no console errors.

## UI app

`ui/` is the React comparison app, built by Vite into `desktop/build/renderer` by `npm run build:desktop`, and served by Vite in development. `ui/src/desktop.d.ts` types the desktop bridge, `window.wio`. React and Vite are dev dependencies only, since the app runs from the built files.

- **Thin:** the app talks only to the app API and holds no image logic. It reuses the engine's wording, constants and checks by importing modules with no Node imports: `src/cli/format.ts` (sizes, percentages, quality, totals, verdict meanings and ratings), `FORMAT_NAMES` (`src/inspect/formatNames.ts`, the one list of display names), `METADATA_SUMMARY`, `keptBySuiteChain`, `readAppOptions`, and from `resolveSettings.ts` `PIPELINE_TARGET_PRESETS`, `PIPELINE_RIGHTS_OPTIONS`, `isMaxWidth` and `rightsFieldError`. Everything else it takes from `src/` is `import type`, such as the contract's types and `src/app/api.ts`'s. Vite bundles only what the app imports as values, and `tests/dist.test.ts` checks the built scripts hold no zod, sharp or SVGO, when that build exists.
- **State:** `readEvents.ts` parses the event stream, because `EventSource` can't POST. `refs.ts` turns a ref into the address the app serves its file at.
- **Images:** `images.ts` is the opened images' reducer: queued, processing, done or failed, and `replaced` once a save has replaced the original. Opening an image already open changes nothing, unless it was replaced, when the new file is queued. `useImages` runs the queued images through `/api/optimise` one batch at a time, runs every image again when the max width changes, and rewrites the outputs through `/api/rights` when the metadata options change. An image that finishes while the options are still changing waits for them to settle, and is rewritten if they settle on metadata other than its run's.
- **Options:** `useAppOptions` loads the options bar's values through `window.wio.loadOptions`, and saves them once they have settled for 300 ms, never before the loaded values have. Until then its `settings` are `undefined`, so nothing runs or searches on a half-typed value. `settingsOf` keeps the fields a run takes through `readAppOptions`, main's own check, and sends no rights with Remove all metadata, which the API refuses.
- **Viewer:** `ComparisonViewer` is the main view of one image's result (`comparison.ts`: `canCompare`, the panes' order and titles). Every pane shares one `Viewport` state, a zoom in device pixels per image pixel (so 1 is 1:1 on any display) and the image point at the panes' centre, or `fit`. `viewport.ts` holds its maths, pure: `layoutOf` places the image at whole device pixels and pixelates above 1, and the centre is clamped so the image fills the pane. Sync needs panes of one size, so the grid's panes share their header rows through `subgrid`. `ImageViewport` draws stacked layers (the output, its diff map at an opacity, the original clipped for a wipe), keyed by their `alt`, so a new re-encode swaps into the same `<img>` and the old image shows until it decodes, measures itself with `ResizeObserver`, and pans and zooms through the shared setter; its wheel listener is added natively, because React's is passive.
- **Panes:** `panes.ts` builds a comparison's panes: a raster suite, any result without a `same` output, since the app runs every raster image as a suite, always has AVIF, WebP and fallback panes. An AVIF or WebP the run left out is an empty pane with a slider to find its output, and a missing fallback an empty pane with none, since only the run chooses between JPEG and PNG. Each pane shows the run's output or its latest search's, as an output, and `keptBySuiteChain` over what the panes show now marks which the suite keeps (never one larger than its original) and says why the others aren't ("Not in the suite: no smaller than the WebP"), so Save suite's contents are visible. `useTargetSearches`, held by `App` so a slider outlives its viewer, keeps each pane's target slider (50 to 100 in steps of 5, since a single point makes little visible difference, the `PIPELINE_TARGET_PRESETS` marked on it, starting at the run's target), asks `/api/search` 150 ms after it rests, and keeps one request per pane in flight, asking for the latest target when it returns (unless unmounted), so a drag doesn't queue a search per step. A change to the width or the metadata options makes its results stale, so the sliders go back to the run's outputs. `useDiffOverlays` keeps each pane's overlay setting and draws the map of the image the pane shows now, from an effect, so an overlay follows the slider.
- **Saving:** `useSaves`, also held by `App`, keeps each pane's save through `window.wio.saveOutput`, and the note from `saveSuites`, which Save suite (one image's kept panes), Save all and the menu's Save all (every finished image's, by `saveAll` in `App`, counting the unfinished, failed or replaced ones as skipped) share. The page passes refs only. A save that replaced its original marks the image `replaced` through `useImages`, and its viewer drops the sliders and Save buttons, since every comparison is then against an old original. Opening it again runs the new file, and `App` first clears its panes' sliders and saves (`paneKeysOf`).
- **Styles:** one stylesheet, `styles.css`, with the colours as tokens on `:root` through `light-dark()`, so the page follows the system theme. States are `data-*` attributes.
- **Types:** `ui/tsconfig.json` is a browser config (DOM, bundler resolution) that also includes `tests/ui/`, so its setup file and component tests are checked with the DOM's types. It loads Node's types too, because the contract's types come from engine source that names `Buffer`, and ESLint forbids `Buffer`, `process` and `require` in `ui/` instead. `tsconfig.test.json` leaves `tests/ui/` out, and `npm run typecheck` runs both.
- **Tests:** `tests/ui/*.test.ts` unit-tests the pure modules without a DOM. `tests/ui/*.test.tsx` are smoke tests of the components with React Testing Library, in Vitest's `dom` project on happy-dom (jsdom needs a newer Node 24 than the engines field allows), whose setup file, `tests/ui/setup.ts`, cleans up after each test. `fetch` is stubbed per test through `tests/ui/fetchStub.ts`, and the slider's debounce is checked with fake `setTimeout`s. `tests/ui/results.ts` holds finished results to render.

## Thin entry points

The CLI (`src/bin/`, `src/cli/`), the app API (`src/app/`), the desktop shell (`desktop/`) and the UI (`ui/`) hold no image logic. They parse input, call the engine's functions and stages, and render the results.

- Only the entry points read `process.env` or `process.argv`: `src/bin/`, the desktop's main process entry, `desktop/src/main/index.ts`, which reads `WIO_DEV_SERVER` and its command line, and the two child modules, which read only the scorer count their parent forks them with. Every other module receives its options as arguments. The one exception is `processSlot.ts`, which passes `process.env` on to the children it forks with `UV_THREADPOOL_SIZE` set (see Batches), since libuv reads it only as a process starts.
- No module does work at import time, except the entry points: `src/bin/`, `desktop/src/main/index.ts`, the desktop's preload, the two child modules, `src/pipeline/worker.ts` and `src/app/pixelWorker.ts`, and the score pool's thread, `src/metrics/scoreWorker.ts`, which nothing imports.
- SVGO takes about 250 ms to import, so it is loaded with `await import("svgo")` when the first SVG needs it, and only imported statically as types. The WASM scorer loads lazily for the same reason. zod loads only with the app API, which the CLI never imports.
- Every module in `src/` lives in its own folder with an `index.ts`, which is what other modules import.
- `wio` is an application, not a library: there is no `src/index.ts`, and `package.json` is private with no `exports`, so nothing outside the repo imports a module. The scripts and `tests/dist.test.ts` import a module's build from `dist/<module>/index.js`, and the desktop's main process imports `dist/app` as `#app`, the `package.json` subpath import.
